## Wire mismatches found (expected vs actual)

### 1. `DebuggerHub.Attach` hardcoded `SessionId: 0` breaks every debug session on this server

**Expected** (per `debugger-hub.ts` WIRE comment): `Attach({BreakOnNextClient, SessionId: 0, UserId: null})` establishes a "break on next client" session; `SessionId: 0` is presumably meant as a "not attaching to an existing session" sentinel.

**Actual:** `Attach` and `DebugAdapterConfigurationDone` both return `null` and *appear* to succeed (the `invoke()` promise resolves without throwing), but the server immediately pushes an async `OnFatalDebuggerException`:

```
Attach raw response: null
EVENT OnFatalDebuggerException: ["The specified session with id 0 for debugging cannot be found."]
ConfigurationDone raw response: null
EVENT OnFatalDebuggerException: ["A serious debugger error has occurred. Please restart a debugging session from Visual Studio Code."]
```

Every subsequent hub call on that connection (`AddBreakpoint` included) triggers the same cascading `"A serious debugger error has occurred..."` fatal and returns `null` instead of the documented payload (e.g. `AddBreakpoint` should return a `BreakpointDefinition`/`BreakpointId`, actually returns `null`, so `DebuggerClient.addBreakpoint()` correctly throws `"Server did not return a breakpoint id — breakpoint was not set"`, but the *root cause* is upstream in `Attach`, not in `AddBreakpoint` itself).

Confirmed via `Get-NAVServerSession -ServerInstance BC`: **zero active sessions** at the time of `Attach` — there's no session "0" (or any other) to attach to yet, so the hardcoded literal `0` is very likely wrong; the field may need to be `null`/omitted, or `BreakOnNextClient` mode may require a different call shape than "attach to an existing session by id". This makes every `debug_attach` on this server produce a session that looks attached (`{attached:true, connectionId:...}`) but is non-functional — nothing that depends on a live debug session (breakpoints, break events, variables, eval, IsAlive/heartbeat, step actions) could be exercised as a result. `debug_wait` was still confirmed to work correctly around this: two calls drained the two queued fatal events instantly (0ms), and a third call genuinely waited the full `timeoutMs` (3010ms measured for a 3000ms request) and returned `{timedOut:true}` — the wait/queue mechanism itself is sound, it's just that this server's `Attach` never gives it anything useful to report.

`debug_detach` was still exercised against this broken session and returned `{detached:true}` without error (its `client.stop()` swallows any `StopDebugging` invoke error), so at least the cleanup path is robust to a broken session.

### 2. `dev/metadata` is not authentication-gated on this container

**Expected:** wrong credentials against `dev/metadata` → HTTP 401/403 → `DevEndpointError(kind:"auth")`.

**Actual:** `dev/metadata` returns HTTP 200 with the correct password, a wrong password, a bogus username, and *no* `Authorization` header at all — verified directly with `curl` (four variants, all 200, identical body). This appears to be this container's IIS/site config exposing that specific route anonymously (possibly intentional, since it's just version info). By contrast, the `TestRunnerHub`/`DebuggerHub` SignalR `/negotiate` endpoints **do** enforce credentials correctly (401 for wrong password, 401 for no `Authorization` header) — so BC's credential-checking is not broadly broken, it's specific to this one anonymous route on this container. The CLI's own auth-error handling code path could not be exercised end-to-end here; nothing to fix in the CLI.

### 3. Hub routes require an explicit `tenant` query param, even though `dev/metadata` does not

**Expected:** `tenant` is optional in `ConnectionConfig`/`buildHubQuery` (`if (c.tenant) query.tenant = ...`), matching that `dev/metadata` works fine with no tenant at all.

**Actual:** `POST .../TestRunnerHub/negotiate` (and `DebuggerHub/negotiate`) returns **401 Unauthorized** without a `tenant` query parameter present, even with fully correct Basic-auth credentials — confirmed by direct `curl` (`negotiate?negotiateVersion=1` alone → 401; add `&tenant=default` → 200). This isn't a multi-tenant-only quirk: the container is effectively single-tenant (`default`) and still requires the parameter on hub routes. Any caller of `run_tests`/`debug_attach` that omits `tenant` (as the mission's example tool-call snippet does: `{server, serverInstance}` only) will get an opaque SignalR negotiation 401 with no indication that `tenant` is the missing piece. This is a real trap for callers, worth a doc/README callout (not a code bug — `tenant` being optional is correct when the caller supplies it; the risk is silent omission).

### 4. `run_tests` always emits one extra `TestCompleted` event with an empty `method` field

**Observed** in every run (whether 1, 2, or 3 methods requested, whether all pass or one fails): exactly one trailing `TestCompleted` per codeunit with `method:""`, whose `status`/`output` mirrors the *last* method actually executed in that codeunit (e.g. requesting `["IsTrueTest","ErrorHasNotBeenThrown"]` → real `ErrorHasNotBeenThrown` failure entry, immediately followed by a `method:""` entry with the identical failure text/status). This looks like a codeunit-level rollup result (as opposed to a per-`[Test]`-method result) rather than a bug in the CLI's parsing — the CLI passes it through faithfully as `{method: "", status, output}`. Also observed: a nonexistent method name requested (`"NonExistentMethodXYZ"`) does **not** produce any error/not-found signal — the server silently ignores it (no `TestCompleted` for that name at all; just the usual `OnRun` + real methods + one trailing blank-method rollup, all "passed" in that run). Worth knowing for anyone building on `run_tests`: don't assume every requested method name gets its own `TestCompleted`, and be ready to see a `method:""` row per codeunit in the results array.

### 5. Additional unhandled `TestRunnerHub` client callbacks

Raw probing showed the server also invokes `HubConnected`, `LogServerInfoMessage`, `RuntimeInitialized`, and `TestStarted` (fired once per test method) on the client — none of these are registered in `test-runner-hub.ts`, so `@microsoft/signalr` logs a harmless `"No client method with the name '...' found"` warning for each and drops them. Not a functional problem (nothing currently needs that data), just recorded in case someone later wants `TestStarted`-driven progress reporting.

## New wire mismatches found (round 2)

### 6. `DebugAdapterConfigurationDone` is only valid after the debugger is bound to a session — calling it right after `Attach` throws

**Expected** (current `DebuggerClient.connect()` in `src/core/hubs/debugger-hub.ts`): `Attach` then immediately `DebugAdapterConfigurationDone(DebugOptions)` — both accepted.

**Actual:** with a *healthy* attach (SessionId -1), an immediate ConfigurationDone consistently throws `"An unexpected error occurred invoking 'DebugAdapterConfigurationDone' on the server."` (server-side exception; reproduced 3×: tool run, raw probe, variant probe). A no-arg variant fails with the arity-style message `"Failed to invoke ... due to an error on the server."`, so the 1-arg shape itself is right. The same 1-arg call **succeeds** (`null`) when invoked *while the debugger is attached to a live session* — validated at a break. This matches the decompiled VS Code client's real sequencing (`esp-decomp`): the DAP `initialized` event — the trigger for VS Code to send breakpoints + configurationDone — is only raised from `HubConnected`/`OnAttachedToConnection` (`HubBasedDebuggerService.HubConnected() → DebuggerService.Connected() → DebugAdapterInitializedEvent`), and the server only sends `HubConnected` on the DebuggerHub **once a session binds to the debugger** (observed: no HubConnected after a bare Attach; HubConnected arrives moments after the TestRunnerHub `Initialize` that carries our `debuggingContext`). Round 1's "ConfigurationDone accepted" was an artifact of the broken SessionId-0 session swallowing the call. **Fix direction (not applied):** defer `DebugAdapterConfigurationDone` until `HubConnected`/`OnAttachedToConnection`/first `Break` — or skip it when defaults suffice: server-side defaults already break on error (the Break fired without ConfigurationDone ever being sent, matching decompiled `DebugOptions.Default` = BreakOnErrorBehaviour.All + SkipSystemTriggers). Note `breakOnError:false`/`breakOnRecordWrite:true` overrides currently cannot take effect at all.

### 7. Debugger payloads arrive with keys in BOTH casings; `Break` arg0 is PascalCase-only

The server serializes DebuggerHub payload objects with **duplicated keys** — every field appears in camelCase *and* PascalCase (stack frames carry `methodName` and `MethodName`, `statementSpan.from.line` and `StatementSpan.From.Line`; same for `BreakpointDefinition` and `LocalNode`). Exception: `Break` arg0 (the object id) came PascalCase-only: `{"ObjectNumber":130000,"ObjectType":5}`. `normalizeKeys` handles both cases correctly (Pascal duplicates lower onto identical camel values), so no code change needed — but any future replacement must keep handling *both* casings, not assume one.

### 8. `AddBreakpoint` on a not-deployed object succeeds but poisons the debugged session

`AddBreakpoint` for codeunit 50100 (exists only in `scratch/al-project`, never published) returned a **successful** `BreakpointDefinition` (id `-396624333`) — no error, no "unverified" marker. But the debugged session then started throwing `"The metadata object CodeUnit 50100 was not found. The application might be incompatible with the current compiler..."` inside the running test, changing its observable behavior (the `ASSERTERROR` in `ErrorHasNotBeenThrown` captured the metadata error instead of its expected assert error). Setting breakpoints on objects the server doesn't have silently corrupts the debuggee. Worth a doc warning; `discover_tests`-style existence checks can't help since the index is client-side only.

### 9. Debugger-slot release after `StopDebugging` is asynchronous — an immediate re-`Attach` fails transiently

Back-to-back attach/detach cycles (5 fresh connections in quick succession) showed alternating failures: an `Attach` issued immediately after a previous connection's `StopDebugging`+disconnect throws `"An unexpected error occurred invoking 'Attach' on the server."` + `OnFatalDebuggerException`, then works again moments later. The server frees the per-user debugger registration asynchronously. Practical impact: rapid `debug_detach` → `debug_attach` can fail transiently; a single delayed retry would make the tool robust (recorded, not implemented).
